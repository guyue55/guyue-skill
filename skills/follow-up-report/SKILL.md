# Follow-Up Report (跟进汇报整理)

> [!NOTE]
> 专门用于将日常客户沟通、零散信息转化为规范的、带有明确格式的阶段性跟进汇报。

## When to Use

当用户提供一段日常沟通记录、会议零散要点，或明确要求“生成跟进汇报”、“整理客户跟进记录”时触发此技能。

## Anti-Patterns to Avoid

- **自行脑补事实**：绝对禁止编造未提供的时间、客户名称、进展细节或测试安排。
- **平铺直叙无重点**：禁止生成没有层级、没有加粗高亮的流水账。
- **格式偏离**：禁止改变要求的固定结构（一、主要沟通内容；二、当前阶段；三、待办）。
- **遗漏信息**：禁止遗漏用户提供的任何有价值的信息（如责任方、特定条件等）。

## Step-by-Step Execution

1. **信息收集与评估**：
   - 提取用户的零散信息，识别核心要素：项目/客户名称、汇报日期、沟通内容、当前阶段、待办事项及其责任方。
   - 若关键信息严重缺失（如客户名称、日期、核心进展等），主动向用户追问以补齐（例如：“请问汇报日期是哪天？”“是否有具体的待办事项？”），直到信息足够生成完整汇报。

2. **结构化处理**：
   按照以下规范结构进行整理：
   - **标题**：`**[客户或项目名称] 客户跟进汇报（[日期]）**`（必须加粗）
   - **一、主要沟通内容**：提炼几个核心方向，以 `- **[核心点]**：[具体详情]` 的列表格式呈现。注意每个要点的标题要加粗。
   - **二、当前阶段**：用简练的段落或列表描述当前所处的整体进度，说明卡点或待客户确认的事项。
   - **三、待办**：以有序列表 `1. [事项] --[责任方]` 呈现。

3. **输出排版**：
   - 严格应用 Markdown 加粗，确保标题和核心要点醒目。
   - 确保层级分明，无多余的客套话。

## Showcase (展台)

**输入示例：**
客户是深圳岍丞，今天是10月9号。今天跟他们调了回调接口，没问题了，能重试，也能扩容。知识库能传和删了，但接口文档还要我们给（webeye）。他们得定好异常标准和知识库才能测。测完没问题才算第一阶段验收。现在就是等他们定稿和定测试时间。

**输出规范示例：**

**深圳岍丞 Agent 项目客户跟进汇报（10月9日）**

**一、主要沟通内容**
- **接口联调进展**：回调接口已接入现有接口体系，全链路测试通过，返回值及传参正常；已具备错误重试机制，高峰负载可通过扩容应对。
- **知识库能力**：已支持文件上传、删除，内容更新可通过删除旧文件、上传新文件实现，相关接口说明待补充。
- **测试及验收安排**：双方明确，需先统一最终版知识库与异常检测标准，再开展真实数据测试；返回结果符合业务标准、问题整改完成且无遗留问题后，完成第一阶段验收。

**二、当前阶段**
项目处于接口链路验证通过、真实业务数据测试待启动阶段。
当前客户异常判断标准和知识库内容未最终定稿，需等待客户定稿后进行实际测试。

**三、待办**
1. 确定异常规则和知识库定稿时间 --客户
2. 确定正式测试时间 --客户
3. 提供知识库接口调用文档 --webeye

## Guardrails (诚实边界)

- 绝不代表客户或内部做出任何未经用户提供的承诺。
- 当指派责任方时（如待办中的 `--客户` 或 `--webeye`），必须基于原始信息的合理推断或原文。如果无法确定责任方，必须留空或询问。

## Cross-Skill Invocation

- 若需要将汇报存档，可调用 `documentation` 或 `memory-bank` 将其归档。
