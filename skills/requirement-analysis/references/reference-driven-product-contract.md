# 参考驱动产品契约

这份契约用于把“一句话产品目标”变成可分工、可检查、可停止的稳定输入。它服务于现有 `product-delivery` 协作链，不是新的万能 Skill，也不替代真实实现、部署、用户反馈或生产验收。

## 使用顺序

1. 先从用户目标中冻结核心场景、当前替代方式、预期结果和不做的后果。
2. 只研究会改变设计或验收的参考对象；记录来源、访问时间、采用的机制、具体适配和权利边界。
3. 对无法从现场推断且会改变范围、权限、成本或完成口径的问题，每次只向用户确认一个。
4. 按示例生成 JSON 契约，并运行：

   ```bash
   python3 scripts/check_reference_product_contract.py path/to/product-contract.json
   ```

5. 检查通过后，主控才可按契约分配设计或实现任务。共享状态机、权限、审计和完成口径仍由主控持有。
6. 独立评审使用同一冻结契约和参考映射验收，不允许执行者修改契约、检查器或阈值制造绿灯。

## 必要字段

- `metadata`：契约身份、状态、所有者和决策人。
- `problem`：用户、核心场景、当前替代、目标结果、无变化后果和成功指标。
- `references`：来源、访问时间、可迁移机制、适配方式和反抄袭边界。
- `scope`：必须、建议和明确非目标。
- `domain`：角色、对象、状态和带守卫及审计事件的状态转换。
- `permissions`：主体、动作、资源、范围、后端强制点、前端体现和越权反例。
- `acceptance`：用户承诺、证据等级、检查器、所有者、失败条件和来源引用。
- `loop`：最大轮数、时间、子任务、独立检查器、停止、升级和回滚。
- `delivery`：实现授权、目标阶段、完成定义和已知限制。
- `traceability`：每条参考机制到验收项的适配映射。

## 证据边界

检查器只验证结构、引用、状态、权限反例和循环边界是否完整。它不证明：

- 参考来源的事实一定正确；
- 实现已经发生；
- 产品达到成熟、稳定或生产可用；
- 多 Agent 真的独立；
- 测试、部署、监控、恢复或真实用户价值已经通过。

这些声明仍需 `reality-auditor` 从代码、数据、运行产物和外部状态逐项复核。
