## 2. GATE-001 覆盖复核

GATE-001 要求验证：用户给出产品目标后，古月能找到参考、补问必要信息、组织协作并以外部标准验收，而不是随意生成。组合模拟覆盖情况如下：

| GATE-001 要素 | 覆盖判断 | 证据 | 独立评审意见 |
|---|---|---|---|
| 主动找参考 | 覆盖较强 | TASK-201 列出 6 份原始材料，并将 Agent 编排经验、Linear/Jira/Intercom/Zendesk 工单机制映射到固定契约 | 能证明“参考机制可被抽象”，但不证明当前运行时会自动检索或选择这些参考 |
| 必要澄清 | 覆盖较强 | TASK-301 提出 8 个高影响澄清问题，并给出用户不回答时的默认假设 | 问题质量足够，但缺少可复用入口或机器检查，仍依赖人工控制包 |
| 产品契约 | 覆盖较强 | `product-contract-v1.md` 固定角色、对象、状态机、8 条验收标准和非目标 | 契约紧凑、可验收；但参考到验收仍是文档级映射，不是结构化可检查产物 |
| 多 Agent 分工 | 覆盖中等偏强 | Goal 总控定义 TASK-201/301/302/303 的所有权；TASK-302 给出主控、产品/参考、架构/实现、独立评审的所有权边界 | 生产 Agent 隔离较清楚；但这次是模拟报告组合，不是实际多生产 Agent 实现协同 |
| 主控集成 | 覆盖中等 | Goal 总控持有权威顺序、风险门、委派与收束；TASK-302 明确共享权限、状态机、审计语义必须由主控收束 | 主控职责定义充分；缺少一份已完成的主控集成报告来证明 301/302 冲突已被实际收束 |

总体判断：组合模拟可以覆盖 GATE-001 的“结构链路”，但不能覆盖“当前古月运行时能从普通用户一句话稳定启动该链路”。因此不能直接进入 PHASE-04 做正向能力完成判断，必须先跑唯一活体探针。

## 3. 缺口与反证

### 缺口 A：复合目标入口未证明，且已有反证

PHASE-01 的复合目标路由检查显示，`scripts/explain_route.py "B2B 工单协作产品目标..."` 退出码为 0，但“无直接 Skill 命中，只给出弱相关候选”。这直接反证了“普通用户低门槛一句话进入参考驱动产品工程主链”的自动入口假设。

该反证的重要性高于“能否写出工单状态机代码”，因为 GATE-001 的用户结果首先要求系统能从产品目标进入正确编排，而不是由用户手工拆成参考、产品、工程、评审四份任务。

### 缺口 B：主控集成尚未形成独立产物

TASK-301 与 TASK-302 分别从产品和工程角度给出模拟，但当前指定输入中没有一份主控集成报告，逐项处理两者之间可能的冲突，例如：

- 产品侧说客户或内部成员可提交请求，固定契约更偏内部创建，外部门户后续扩展；
- 工程侧保留管理员状态配置字段，但产品契约把复杂自定义工作流排除在首版外；
- 产品侧验收量表是 10 维评分，工程侧检查器是 C1-C6，二者尚未被统一成唯一验收门。

这些不是阻断探针的缺陷，但会阻止直接宣称“组合模拟已经闭环”。

### 缺口 C：评委回炉还停在标准层

301/302 都定义了返工问题或返工门，本报告也在独立评审，但还没有真实执行一次“评委发现缺口，主控修改契约或集成报告，再由评委复核”的回炉链路。GATE-001 可暂时接受标准层覆盖，但 PHASE-04 必须把证据等级降为模拟级。

### 缺口 D：参考与契约的机器可检查性不足

参考报告能解释机制来源，产品契约能列验收标准，但没有结构化字段或检查器把“每条参考机制 -> 契约条款 -> 探针/测试”稳定绑定。后续如果进入完整产品验证，这会造成验收漂移。

### 缺口 E：当前工作树 dirty，发布级结论必须禁止

PHASE-01 已记录 `scripts/try_guyue.py` 因未发布修改导致包体检查失败。因此即使唯一探针通过，也只能支持“dirty 工作树上的候选能力证据”，不能支持 release-ready、clean 封账或成熟稳定产品完成声明。

## 5. 唯一最小活体探针

### 选择：P1 复合目标路由探针

这是唯一应执行的探针。原因：

1. PHASE-01 已给出最大反证：复合产品工程目标没有直接路由入口。
2. GATE-001 的首要用户价值是“普通用户低门槛启动复杂产品工作”，入口失败会使后续参考、澄清、多 Agent 和评审都继续依赖人工主控。
3. P1 使用现有本地脚本即可完成，不安装、不联网、不写外部系统，35 分钟内可完成。
4. P2 更能验证契约到检查器，P3 更能验证领域规则实现，但二者都绕开了“用户一句话能否进入主链”的最高不确定点。

### 探针命令

在仓库根目录 `repo-root` 执行一次：

```bash
PYTHONDONTWRITEBYTECODE=1 python3 scripts/explain_route.py --json --limit 8 "做一个成熟可用稳定的 B2B 工单协作产品。请主动寻找合适参考，补问必要信息，形成产品契约，组织多 Agent 分工，由主控集成，并用独立评委和可执行检查器验收。首版必须覆盖工单创建、分派、状态机、客户可见性、评论与内部备注、SLA 风险、审计和列表真实筛选；不要复制品牌资产，不要宣称完整成熟 SaaS。"
```

执行约束：

- 只执行一次。
- 不安装依赖。
- 不联网。
- 不重试。
- 不修改 Guyue 核心。
- 记录命令、开始/结束时间、退出码、stdout/stderr 摘要和原始输出路径。

### 通过判据

探针通过必须同时满足：

1. 退出码为 0。
2. JSON 输出中至少出现一个直接 `selected` 路由，或出现明确的 `collaboration_candidates`，其阶段或候选能力能覆盖至少 4 类关键链路：参考研究/来源、需求澄清或产品契约、系统设计/工程拆解、多 Agent 协作/主控、现实审计/检查器/验收。
3. 输出不得只给通用写作、单一编码、单一项目管理或弱相关候选。
4. 输出不得建议安装、联网、部署、提交、修改根 Skill/Manifest，或扩张为完整 SaaS。

### 失败判据

任一情况即为失败：

1. 退出码非 0。
2. 无 `selected` 且无可解释的 `collaboration_candidates`。
3. 候选只覆盖单点 Skill，无法覆盖参考、澄清、契约、多 Agent、主控、评审中的至少 4 类。
4. 输出把成熟完整产品实现、外部资产复制、安装/部署/提交作为默认动作。
5. 输出格式无法解析，导致不能复算路由依据。

### 通过/失败含义

| 结果 | 含义 | PHASE-04 使用方式 |
|---|---|---|
| 通过 | 当前路由入口至少能识别复合产品工程主链骨架，PHASE-01 的“弱路由”反证被部分缓解 | 可进入 PHASE-04，但只能声明“入口骨架候选可用”，不能声明成熟产品工程能力已完成 |
| 失败 | 当前古月仍不能从普通用户复合目标稳定进入参考驱动、多 Agent、验收闭环 | 可进入 PHASE-04 做缺口裁决，但路线应偏向“修复/新增编排入口”，不得进入完整产品验证 |

证据等级：若通过，为 `LIVE_ATTEMPT_MEDIUM`；若失败，为 `LIVE_ATTEMPT_HIGH_NEGATIVE`。理由是该探针真实运行当前本地入口，能直接确认或证伪入口假设；但它不构建产品、不验证真实多 Agent 实现协作，所以正向证据不能升为高等级产品能力证明。

## 6. 是否允许进入 PHASE-04

允许条件性进入 PHASE-04：必须先执行上述唯一探针并把结果作为 ATTEMPT 证据纳入 PHASE-04。无论探针通过或失败，都可以进入 PHASE-04 做三路线裁决；但：
